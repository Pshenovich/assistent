## 2. Правила для агента

1. **Разрешения (классификатор auto mode).**
   - Новый сервер: разрешено пользователем («даю разрешение заходить по SSH на новый сервер Selectel и настраивать его»).
   - Старый Beget: разрешено **только снять копию данных** («даю разрешение заходить по SSH на старый сервер Beget и снять копию данных»). Остановка сервисов там, правка его `.env`, переезд — отдельное «да».
   - Выкатка на прод (`deploy_prod_replace.sh` на боевой хост) — только после явного «катим» / «даю разрешение катить на прод»; разрешение одноразовое.
   - Правка боевого `.env` на сервере — отдельное явное согласие на конкретное действие.
2. **Сеть на Маке пользователя.** Пользователь в РФ, без VPN Claude не работает. Happ (режим TUN, процессы `happd`/`xray` из `/Volumes/Happ …`) перехватывает трафик и ломает соединения к российским хостингам.
   - Признак: соединение «устанавливается» за ~2 мс, порт 8080 нового сервера (закрыт файрволом) выглядит открытым, SSH — «timed out during banner exchange».
   - Обход: пользователь сам выполняет (пароль Мака):
     ```bash
     sudo route -n add -host 161.104.35.44 192.168.0.1
     ```
     ```bash
     sudo route -n add -host 91.229.90.4 192.168.0.1
     ```
     Живёт до перезагрузки или смены Wi-Fi (шлюз может быть другим — `route -n get default`). Проверка: `route -n get 161.104.35.44` → `interface: en0`.
   - Постоянный вариант: Happ → «Список CIDR» (обход туннеля): `161.104.35.44/32, 91.229.90.4/32` (может не примениться без премиума).
   - `curl` по https на Маке идёт через прокси Happ (`127.0.0.1:10809`) — для проверок серверов `curl --noproxy '*'`.
3. **Старый сервер взломан (атака на Beget).** Не заходить туда с `ssh -A`; не ставить туда ничего; данные и `.env` оттуда — проверять на посторонние записи (см. runbook, шаг 2 дня переезда). Все секреты из старого `.env` считать раскрытыми (§6).
4. **Общее рабочее дерево.** Другие сессии пишут код в той же папке. Коммитить только свои файлы, `git status` перед коммитом; не stash/reset. Пока идёт переезд — **другие сессии только коммитят, без выкаток**, `DEPLOY_SSH_HOST` не трогают.
5. **Бот — только в одном месте** (иначе 409 у Telegram). После смены токена (§6) старый бот не подключится сам — это и защита.

## 3. Фаза A — спасение данных (как только Beget ответит)

Триггер: `nc -z -G 5 91.229.90.4 22` успешен и `route -n get 91.229.90.4` → `en0` (иначе это туннель Happ).

1. С Мака (из корня репозитория):
   ```bash
   ./scripts/rescue_old_server.sh
   ```
   Сервисы не останавливает. Делает: копию всех `*.sqlite` (в т.ч. в нестандартных местах) через sqlite backup API + `state.tar.gz` (токены, `.env`, `data/users`, `mail_secret.key`, `mail_attachments/` …) + `letsencrypt.tar.gz` + `obuchat-news.tar.gz` → Мак `~/leo-rescue/<ts>` → S3 `orbita-backups/beget-rescue/daily/<ts>/` → новый сервер `/root/leo-rescue/<ts>`.
   - Старый сервер иногда рвёт SSH на «banner exchange» — скрипт сам повторяет 5 раз.
   - `WARN … _DB_PATH … вне /opt/assistant` — такую базу скопировать вручную.
2. Проверить: `gunzip -t` (скрипт делает), `quick_check` каждой базы, число строк (count_rows из runbook) — сравнить с тем, что было до 01.11 (ориентир: ~4–5 активных, 18 напоминаний на 28.10).
3. Спросить пользователя/поддержку Beget: VPS вернулся **с тем же диском** или восстановлен из их копии (от какой даты)? Если из копии — часть данных за последние дни могла пропасть; сказать пользователю честно.
4. Сообщить пользователю: «данные в безопасности: на Маке, в S3 и на новом сервере».
5. Сразу после — если на старом сервере автозапуском поднялись сервисы Орбиты, это нормально (это всё ещё прод, пока DNS `assistent.networ.ru` на нём). Ничего не останавливать без «да».

**Если Beget не вернётся / данные потеряны** (план Z): данных вне Beget до 01.11 нет. Тогда — запуск Орбиты на новом сервере с нуля: новый токен бота (§6), `maintenance_mode.sh off`, выкатка, DNS `assistent.networ.ru` → новый IP; пользователям — честное объявление. Решение — только пользователя.

## 4. Фаза B — репетиция на реальной копии (до окна переезда)

Цель: проверить **текущий HEAD** (там много невыкаченного — §7) на настоящих данных, на новом сервере, без бота.

1. Данные на новый сервер — из `/root/leo-rescue/<ts>` (уже там после фазы A):
   ```bash
   # на новом сервере
   cd /opt/assistant
   systemctl stop assistant-bot assistant-worker assistant-usage executive-board-bot litestream
   tar xzf /root/leo-rescue/<ts>/state.tar.gz -C /opt/assistant      # .env, токены, data/users …
   for f in /root/leo-rescue/<ts>/*.sqlite.gz; do n=$(basename "$f" .gz | sed 's#__#/#g'); gunzip -c "$f" > "/opt/assistant/$n"; done
   rm -f /opt/assistant/*.sqlite-wal /opt/assistant/*.sqlite-shm /opt/assistant/data/*.sqlite-wal /opt/assistant/data/*.sqlite-shm
   ```
2. В `/opt/assistant/.env` нового сервера (это теперь копия старого `.env`): `TELEGRAM_BOT_TOKEN=` **пустой** и `S3_BACKUP_PREFIX=orbita-rehearsal` — на время репетиции. Сверить `.env` на посторонние ключи/адреса (атака).
3. Выкатка только на новый сервер, общий `.env` не трогаем:
   ```bash
   DEPLOY_SSH_HOST_OVERRIDE=161.104.35.44 ./scripts/deploy_prod_replace.sh
   ```
   (тесты гоняет сам; зависимости — по `requirements.lock`; ставит nginx-сайты, Litestream, патч сжатия nginx).
4. **Сразу после выкатки** вернуть заглушку — выкатка заново включает сайт getorbita.me, и приложение с реальными данными стало бы доступно людям:
   ```bash
   ssh root@161.104.35.44 'bash /root/maintenance_mode.sh public'
   ```
   (скрипт идемпотентен: снимает включённые деплоем сайты, возвращает https; лежит и в репо `scripts/maintenance_mode.sh`).
5. Проверки на сервере: `curl -H 'Host: assistent.networ.ru' http://127.0.0.1:8080/healthz` (503 из-за отсутствия бота — норма), `journalctl -u assistant-usage --since -10min | grep -iE 'error|traceback'` — миграции схем прошли без ошибок; count_rows совпадает с копией.
6. Посмотреть приложение глазами, не открывая его людям (заглушка закрывает все домены): туннель
   `ssh -i ~/.ssh/leo_server -N -L 18080:127.0.0.1:8080 root@161.104.35.44` и в браузере `http://localhost:18080/webapp/`
   (вход по коду из бота не сработает — бота нет; смотреть списки/документы через dev-вход, если нужен — с пользователем).
7. После репетиции: `systemctl stop litestream` и удалить в S3 префиксы `orbita-rehearsal/` и `litestream/orbita-rehearsal/` (код удаления — как в истории 02.11: `backup_s3.S3.list/delete`).

## 5. Фаза C — окно переезда (~30–45 мин, вечер, время согласовать с пользователем)

Порядок — runbook «День переезда». Отличия и уточнения на сейчас:

1. Старый сервер: остановить и выключить автозапуск сервисов Орбиты (отдельное «да» пользователя).
2. Финальная копия данных при остановленных сервисах — либо rsync одноразовым ключом (runbook), либо повторный `./scripts/rescue_old_server.sh` + распаковка как в фазе B.1. Перенести `/etc/letsencrypt`, `/opt/obuchat-news`, unit-файлы `assistant-news-sync.*`.
3. count_rows старый = новый, один в один.
4. На новом `.env`: **убрать** `S3_BACKUP_PREFIX=orbita-rehearsal`; вписать **новые** секреты (§6), в т.ч. новый `TELEGRAM_BOT_TOKEN`; проверить `WEBAPP_PUBLIC_URL`, `GOOGLE_OAUTH_REDIRECT_URI`, `ZOOM_OAUTH_REDIRECT_URI` (уже на getorbita.me — переносит ENV_SYNC из локального `.env`).
5. `bash /root/maintenance_mode.sh off` (вернёт сайты и сертификат getorbita.me).
6. Локальный `.env`: `DEPLOY_SSH_HOST=161.104.35.44`. Затем (после «катим»):
   ```bash
   ./scripts/deploy_prod_replace.sh
   ```
7. DNS в мини-админке Beget: `assistent.networ.ru` → `161.104.35.44` (getorbita.me уже там). Подождать 5 мин.
8. https для `assistent.networ.ru`: если `/etc/letsencrypt` перенесён — `certbot --nginx -d assistent.networ.ru` переиспользует; иначе выпустит заново после DNS.
9. Проверки из runbook (healthz 200 + пульс бота, вход, напоминание, ответ бота, журнал без traceback, Sentry). Плюс бэкапы: `systemctl is-active litestream`, `python3 /opt/assistant/scripts/backup_s3.py list`, в S3 появился `litestream/orbita/…`.
10. BotFather: menu button / Web App URL мини-приложения — проверить, что ведёт на рабочий адрес.
11. Откат — runbook (первые 15 минут). Со сменённым токеном откат требует вписать новый токен и на старый сервер.

## 8. После переезда (по порядку)

1. **Неделю** старый сервер держим выключенным (сервисы Орбиты остановлены), но не удаляем. Мелкие проекты (insurance-app, netw-*, tchk-postgres, next-server, pm2, warp-proxy) остаются там.
2. Удалить с нового сервера мусор репетиции: `/root/leo-rescue/*` (после проверки), cert `leo-maintenance` можно оставить.
3. **Перенос DNS в Selectel** (решено: Selectel DNS — бесплатно, есть API для автопереключения; reg.ru бесплатно только для своих доменов). Шаги для пользователя — в истории сессии 03.11; кратко: зона в «DNS-хостинг» Selectel → записи по скриншотам из Beget (в т.ч. MX `mx1/mx2.beget.com` и SPF для почты support@getorbita.me и networ.ru) → в Beget NS → `a/b/c/d.ns.selectel.ru`. Сервисный пользователь Selectel с ролью DNS → `SELECTEL_DNS_USER`/`SELECTEL_DNS_PASSWORD` в `.env`.
4. **Пожелания пользователя к отказоустойчивости** (02.11):
   - каждая выкатка на основной сервер дублируется на запасной (сервисы там выключены);
   - ночные бэкапы в два S3 (Selectel + второй поставщик);
   - автопереключение: запасной пингует основной; 5 мин тишины → восстановление из S3, запуск, смена A-записей через DNS API, сообщение в Telegram; **возврат на основной — кнопкой в `/dashboard`** (данные с запасного переносятся обратно); «аренда главного» в S3, чтобы двух Орбит не было; статус обоих серверов, последние выкатка/бэкап — в дашборд.
   - Запасной на Beget — пересмотреть после атаки (лучше другой поставщик). Оценка: п.1–2 ~1 день, п.3 с дашбордом ~2–3 дня.
5. Этап 0/1 из плана масштабирования: сервисы не от root (`LEO_NONROOT=1`), мониторинг Selectel, внешний пинг `/healthz`, удаление кода Vexa.
