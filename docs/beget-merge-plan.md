## 1. Принцип

**Старое вливается в новое** (в копию новых баз), а не наоборот: новые таблицы (аккаунты, БЗ организаций,
отделы, сейфы, макеты) есть только в новом. Старые строки получают номера < 10 000 000, новые ≥ 10 000 001 —
**первичные ключи AUTOINCREMENT не пересекаются**, ссылки между таблицами (документ ↔ листы ↔ версии ↔
Yjs ↔ комментарии ↔ задачи) остаются верными без перенумерации.

Перед копированием старые файлы баз один раз открываются **кодом HEAD** (сторы делают `ALTER ADD COLUMN`
при открытии) — колонки выравниваются со схемой нового. Строки переносятся с явным списком общих колонок.

**Ничего не удаляется** на новом проде: при конфликте побеждают новые данные, старые — либо дополняют,
либо попадают в отчёт «не перенесено, решить вручную».

## 2. Ответы на вопросы

### 2.1 Куда ложатся старые документы, как не задвоить

- Старые документы ложатся **личными документами своих владельцев** (`local_notes.user_id` = владелец после
  сопоставления людей, п. 2.2). В БЗ организаций **само ничего не попадает**: `org_kb_nodes` в старых данных нет,
  создавать узлы автоматически не будем.
- **Решение владельца (09.11): все старые документы базы знаний — авторам в «Документы».** «Так они не
  потеряются и не будет конфликта; авторы сами распихают их по разделам новой БЗ». В старой схеме БЗ — это
  подключённые источники (`knowledge_bases` + `kb_documents` + `kb_chunks`, доступ `kb_members`; синхронизация
  из Google Docs / Notion / Яндекс Диска / Битрикс24). Каждый `kb_documents` (kb_id, doc_id) собирается в **один
  обычный личный документ**:
  - владелец — `knowledge_bases.owner_telegram_user_id` (после `owner_map`); отдельного автора у документа в
    старой схеме нет;
  - заголовок — `kb_documents.title` (пустой → название базы); текст — `kb_chunks` по `chunk_index`, заголовки
    кусков (`heading`) — подзаголовками;
  - `meta_json`: `{"imported_from": "old_kb", "kb_title": …, "source_url": …, "source_type": …}` — откуда пришёл;
  - **без** привязки к разделам/узлам новой БЗ, **без** старых прав (`kb_members` не переносим), **без**
    синхронизации с источником (сами `knowledge_bases`/`kb_documents`/`kb_chunks` в новые базы не кладём);
  - правила дублей (ниже) — те же: если автор уже перенёс этот текст на новом (в т.ч. в раздел БЗ), документ
    не создаётся, в отчёте ссылка на новый.
- Обычные старые документы (`local_notes`, в т.ч. с `kb_enabled=1` — это лишь «учитывать в ответах Лео»)
  остаются личными документами как есть; старые совместные доступы (`note_members`, `teams`) — как были.
- Документы БЗ по новому правилу (d5eaff2) не видны в «Документах» — старые личные документы этим не
  затрагиваются.
- **Задвоение** (человек уже пересоздал документ на новом, в т.ч. в разделе БЗ): для каждого старого документа
  ищем новый документ того же владельца или его организации с тем же нормализованным заголовком **или** с
  совпадающим текстом (хэш нормализованного тела; для похожих — доля общих строк ≥ 0,8).
  - Полное совпадение текста → старый **не переносим**, в отчёте «уже есть на новом: <новый id>».
  - Похожий / тот же заголовок → **переносим** с пометкой в заголовке «(до 01.11)» и строкой в отчёте
    «возможный дубль: старый N ↔ новый M» — владелец решает, удалить ли.
  - Решение по умолчанию консервативное: данные не теряются, дубли видны.

### 2.2 Идентичность (почта, синтетические id)

Ключ людей во всех таблицах — `user_id` (Telegram id T; у входа по почте — синтетический S ≥ 5e15).
Связь хранится только в `accounts.tg_user_id` и `account_aliases` (`assistant/stores/accounts.py`).

Карта переноса `owner_map` (строится автоматически, печатается в отчёт до применения):

| Случай на новом | Что делаем со старыми строками T |
|---|---|
| `accounts.user_id = T` (вошёл через бота или привязал без истории) или аккаунта нет | Оставляем T |
| `accounts.user_id = S`, `tg_user_id = T` (вошёл по почте, привязал Telegram) | **T → S** во всех колонках владельца (список — п. 3) |
| `account_aliases(old → new)` | old → new (по цепочке) |
| S без Telegram | Автоматически не связываем. Старые данные остаются под T. Когда человек привяжет Telegram в новом, сработает `merge_into_legacy` (у T уже будет история, у S документов нет) — аккаунт сам переедет на T |

Сейчас под правило «T → S» попадает **один человек**. Сопоставление «по почте» без привязки Telegram — только
вручную, по списку из отчёта, с подтверждения владельца.

Колонки-владельцы, которые переписываются по `owner_map` (не только `user_id`): `owner_user_id`,
`member_user_id`, `author_user_id`, `assignee_*`, `created_by`, `verified_by`, `lead_user_id`,
`owner_telegram_user_id`, `telegram_user_id`, `owner_uid`; строки-принципалы `u:<uid>` в `org_kb_acl` / `vault_acl`;
владельцы `sem_sources/sem_chunks.owner_user_id`; имена файлов `data/users/<uid>.json`, `*_user_tokens/<uid>.json`,
`data/zoom_recent_meetings/<uid>.json`, `mail_attachments/<uid>/`.

Не переписываются «сырые» Telegram id: `chat_digest.sqlite` (участники и отправители в группах, подписки на
срочные), `usage.sqlite` (учёт вызовов — админка сама сворачивает Telegram в аккаунт), `site_chat.sqlite`.

### 2.3 Организации и команды старого формата

- Старый формат — те же `orgs / org_members / org_domains / org_invites / org_settings / org_dismissed`, роли
  owner/admin/member; отделов, БЗ, сейфов не было.
- Старая организация, совпадающая с новой (тот же домен в `org_domains`, или тот же `slug`, или то же название
  + владелец после `owner_map`), **сливается в новую**: переносим только **участников**, которых нет в новой
  (роль — старшая из двух), и приглашения, которых нет. Настройки, домены, `org_groups` — **как на новом**.
- Старая организация без пары на новом — переносится целиком (id < 10M, slug при совпадении — с суффиксом),
  в отделы не раскладывается.
- Отделы/команды (`org_groups`) из старых данных **не создаём** — их не было; участники попадают в
  организацию без отдела, раскладывает админ.
- `credits.org_member_ai.org_id` (TEXT) и `org_contact_grants.org_id` — переписать по карте org_old → org_new.

### 2.4 Миграции схемы

- Старые файлы баз копируются в каталог репетиции и открываются **кодом HEAD** (все сторы) — guarded
  `ALTER ADD COLUMN` и `CREATE TABLE IF NOT EXISTS` проходят на старых файлах (в т.ч. `user_profiles.custom_*`,
  `org_members.tg_hint/guest`). Данные-миграции при открытии: `calendar_tasks._migrate_checklists`,
  `reminders._import_legacy_once` — проверить, что отработали и не задвоили.
- Проверка на репетиции: `PRAGMA quick_check`, сверка числа строк «старое + новое − пропущенное = итог»
  по каждой таблице; открыть объединённые базы сервером (временный `assistant-usage` на другом порту
  против каталога репетиции) и пройти API: список документов, документ с листами/версиями, задачи,
  напоминания, организация, БЗ.

### 2.5 Семантический индекс

- Старые `sem_sources/sem_chunks` вставляем (с `owner_map`); ключи `note:N` < 10M не пересекаются.
  `semantic_memory.index_docs()` сам переносит старые личные копии в секции `doc:<note_id>` и вычищает дубли
  (da87788, 55ac4dc).
- После слияния — полный проход `index_all()` (bot/semantic_index_job.py) несколько раз, пока не перестанет
  находить работу (бюджеты 400 чанков). Неизменённые источники пропускаются по `content_hash`.

  отработанными без отправки**, повторяющиеся — перенести на ближайшее будущее срабатывание (как 4980187).
  В отчёт — список «пропущенных за простой», владелец решает, прислать ли людям одну сводку.
- Приглашения на встречи: объединение `meeting_invites_notified` + baseline (31bd89f) — повторов не будет.
- Срочные из чатов: сдвиг курсора (см. выше).
- Задачи с прошедшими дедлайнами: без отдельных уведомлений, видны в списках как просроченные.
